## 3. `ImportGraphState` 的作用

你标记的 [state.py](/Users/lwj/AI_project/RAG/app/import_process/agent/state.py:5) 是整个入库流程的数据总线。

它虽然叫 `TypedDict`，但运行时仍然只是普通 Python 字典，不提供 Pydantic 那样的运行时校验。LangGraph 把它依次交给每个节点，节点修改字段后传给下一个节点。

主要字段可以分为：

- 任务标识：`task_id`
- 路由字段：`is_pdf_read_enabled`、`is_md_read_enabled`
- 文件路径：`local_file_path`、`local_dir`、`pdf_path`、`md_path`、`file_title`
- 文档数据：`md_content`、`chunks`
- 业务实体：`item_name`
- 预留字段：各种切分开关、`split_path`、`embeddings_path`、`embeddings_content`

其中这些字段目前只是声明了，但没有参与真实逻辑：

```text
is_normal_split_enabled
is_silicon_flow_api_enabled
is_advanced_split_enabled
is_vllm_enabled
split_path
embeddings_path
embeddings_content
```

实际向量直接写进了 `state["chunks"]`，没有使用 `embeddings_content`。
`create_default_state()` 和 `get_default_state()` 都使用深拷贝，避免多个任务共享同一个 `chunks` 列表，这一点是正确的。

### 4.5 文档分块

[node_document_split.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_document_split.py:326) 的设计是：

- 按 Markdown `#` 到 `######` 标题切分。
- 忽略代码块中的 `#`。
- 没有标题时整篇作为“无标题”块。
- 超过 2000 字符时用 `RecursiveCharacterTextSplitter` 二次切分。
- 二次切分重叠 100 字符。
- 目标是合并小于 500 字符的相邻短块。
- 将分块备份到 `chunks.json`。

初始 Chunk 形式：

```json
{
  "title": "## 设备",
  "content": "## 设备\n具体正文……",
  "file_title": "hak180产品安全手册",
  "parent_title": "## 设备",
  "part": 1
}
```

现有样例 [chunks.json](/Users/lwj/AI_project/RAG/output/20260803/5b751c68-8c12-46cb-9a16-69dd8cd32759/chunks.json) 有 14 个 Chunk。

### 4.6 产品名称识别

[node_item_name_recognition.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_item_name_recognition.py:304)：

- 最多取前 5 个 Chunk。
- 单块最多取 800 字符。
- 总上下文不超过 2500 字符。
- 调用文本大模型提取品牌、型号和产品名称。
- 调用失败时用 `file_title` 兜底。
- 将结果写入 State 以及每一个 Chunk。

例如：

```python

chunk["item_name"] = "BrotherHAK180烫金机"
```

同时为产品名生成一组 BGE-M3 双向量，存入 `kb_item_names`。

### 4.7 向量生成

[node_bge_embedding.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_bge_embedding.py:19) 每次处理 5 个 Chunk，实际送入模型的文本是：

```text
主体：BrotherHAK180烫金机，内容：Chunk正文……
```

输出：

```python
{
    "dense": [
        [0.013, -0.027, ...]       # 1024 个浮点数
    ],
    "sparse": [
        {
            1173: 0.1699,
            3895: 0.2170,
            33831: 0.2685
        }
    ]
}
```

- Dense：`list[float]`，维度为 1024。
- Sparse：`dict[int, float]`，键是词表维度，值是权重。
- 序列化成 JSON 后，Sparse 的整数键会变成字符串键。

最终 Chunk 形式：

```python
{
    "chunk_id": 468027378355146793,
    "title": "## 设备",
    "parent_title": "## 设备",
    "part": 1,
    "file_title": "hak180产品安全手册",
    "item_name": "BrotherHAK180烫金机",
    "content": "……",
    "dense_vector": [1024个浮点数],
    "sparse_vector": {维度索引: 权重}
}
```

### 4.8 Milvus 存储

`kb_item_names`：
```text
pk               INT64，自增主键
file_title       VARCHAR
item_name        VARCHAR
dense_vector     FLOAT_VECTOR(1024)
sparse_vector    SPARSE_FLOAT_VECTOR
```
`kb_chunks`：

```text
chunk_id         INT64，自增主键
content          VARCHAR
title            VARCHAR
parent_title     VARCHAR
part             INT8
file_title       VARCHAR
item_name        VARCHAR
dense_vector     FLOAT_VECTOR(1024)
sparse_vector    SPARSE_FLOAT_VECTOR
```

Dense 使用 HNSW + COSINE；Sparse 使用倒排索引 + IP。

```mermaid
    E -->|Markdown| I
    P --> I["图片处理<br/>视觉模型摘要 + MinIO URL"]
    I --> C["Markdown 切片<br/>标题切分 + 长文本二次切分"]
    C --> N["LLM 识别 item_name"]
    N --> IN["Milvus: kb_item_names"]
    N --> V["BGE-M3 双向量<br/>Dense[1024] + Sparse"]
    V --> CH["Milvus: kb_chunks"]
    CH --> DONE["任务状态 completed<br/>前端轮询 /status"]

    Q["chat.html"] --> QS["query_server.py<br/>当前没有业务路由"]
    QS -. "设计目标" .-> QG["QueryGraphState"]
    QG -.-> PIPE["商品确认 → 三路召回<br/>→ RRF → Rerank → 回答"]
```

## 二、`ImportGraphState` 是怎样工作的
`ImportGraphState` 虽然写成 `TypedDict`，但运行时本质上仍是普通 Python 字典，不具备 Pydantic 那样的运行时校验。

`create_default_state()` 和 `get_default_state()` 使用深拷贝，是为了避免不同任务共享同一个 `chunks` 列表。
字段可以分成几类：

- 任务标识：`task_id`
- 路由标志：`is_pdf_read_enabled`、`is_md_read_enabled`
- 输入输出路径：`local_file_path`、`local_dir`、`pdf_path`、`md_path`、`file_title`
- 核心内容：`md_content`、`chunks`、`item_name`
- 预留但未使用：`split_path`、`embeddings_path`、`embeddings_content`
- 尚未接通的切片策略：`is_normal_split_enabled`、`is_silicon_flow_api_enabled`、`is_advanced_split_enabled`、`is_vllm_enabled`

也就是说，虽然状态中设计了四种切片模式，目前代码始终使用同一套普通 Markdown 切片逻辑，这些开关不会改变工作流。

入库任务刚开始时大致是：

```python
{
    "task_id": "UUID",
    "local_file_path": "/.../manual.pdf",
    "local_dir": "/.../output/20260803/UUID",
    "is_pdf_read_enabled": False,
    "is_md_read_enabled": False,
    "pdf_path": "",
    "md_path": "",
    "md_content": "",
    "chunks": [],
    "item_name": ""
}
```

LangGraph 每执行一个节点，就修改这个状态，再交给下一个节点。入库节点主要采用“原地修改字典并返回完整状态”的方式。

## 三、入库数据如何流动

### 1. 上传文件

[import_server.py](/Users/lwj/AI_project/RAG/app/import_process/api/import_server.py:93) 接收：

```text
Content-Type: multipart/form-data
files: PDF 或 Markdown 文件，可重复出现
```

每个文件保存为：

```text
output/YYYYMMDD/{task_id}/{原始文件名}
```

响应格式：

```json
{
  "code": 200,
  "message": "文件上传完成, 文件数量: 1",
  "task_ids": ["5b751c68-..."]
}
```

前端每两秒请求：

```http
GET /status/{task_id}
```

返回：

```json
{
  "code": 200,
  "task_id": "...",
  "status": "processing",
  "done_list": ["开始上传文件", "检查文件"],
  "running_list": ["PDF转Markdown"]
}
```

### 2. 识别文件类型
`node_entry` 根据文件后缀设置：
```python
{
    "is_pdf_read_enabled": True,
    "pdf_path": "/.../manual.pdf",
    "file_title": "manual"
}
```

只识别小写 `.pdf` 和 `.md`。

### 3. PDF 转 Markdown

[node_pdf_to_md.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_pdf_to_md.py:80) 的流程是：

1. 向 MinerU 申请预签名上传 URL。
2. PUT 上传 PDF 原始字节。
3. 每 3 秒轮询一次，最长等待 10 分钟。
4. 下载 MinerU 返回的 ZIP。
5. 解压并选择“原文件名.md”“full.md”或第一个 Markdown。
6. 将 Markdown 全文读入 `state["md_content"]`。

中间产物包括 PDF、ZIP、Markdown、图片、布局 JSON、MinerU 内容 JSON 等。

### 4. 图片处理

[node_md_img.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_md_img.py:316)：

1. 查找 Markdown 同目录下的 `images/`。
2. 只处理 Markdown 中实际引用过的图片。
3. 截取图片前后各 100 个字符作为上下文。
4. 图片转 Base64，与上下文一起发送给视觉模型。
5. 视觉模型生成不超过 50 字的中文说明。
6. 上传图片到 MinIO。
7. 把原引用替换为：

```markdown
![视觉模型生成的图片说明](http://minio/bucket/upload-images/文档名/图片.jpg)
```

8. 保存成 `{原文件名}_new.md`。

实际产物可见 [hak180产品安全手册_new.md](/Users/lwj/AI_project/RAG/output/20260803/5b751c68-8c12-46cb-9a16-69dd8cd32759/hak180产品安全手册/hak180产品安全手册_new.md)。

### 5. Markdown 切片

[node_document_split.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_document_split.py:326)：

- 先按 `#` 到 `######` 标题切分。
- fenced code block 中的 `#` 不作为标题。
- 大于 2000 字的块用 `RecursiveCharacterTextSplitter` 再切。
- 二次切分重叠 100 字。
- 原设计会合并小于 500 字且同属一个父标题的块。
- 结果先备份到 `chunks.json`。

基础切片格式：

```json
{
  "title": "## 设备",
  "content": "该标题下的 Markdown 内容……",
  "file_title": "hak180产品安全手册",
  "parent_title": "## 设备",
  "part": 1
}
```

现有样例 [chunks.json](/Users/lwj/AI_project/RAG/output/20260803/5b751c68-8c12-46cb-9a16-69dd8cd32759/chunks.json) 有 14 个切片。

注意：这个文件是在商品识别和向量生成之前备份的，所以里面没有 `item_name`、向量和 `chunk_id`；这些字段只存在于后续内存状态和 Milvus 中。

### 6. 识别主体名称

[node_item_name_recognition.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_item_name_recognition.py:304)：

- 取前 5 个切片。
- 每块最多取 800 字。
- 总上下文最多 2500 字。
- 将文件名和切片内容传给 LLM。
- 识别失败时使用 `file_title` 兜底。
- 把结果同时写入 `state["item_name"]` 和每个 chunk。

日志中已经成功识别过：

```text
BrotherHAK180烫金机
```

随后单独为商品名生成双向量，并写入 `kb_item_names`。

### 7. BGE-M3 向量化

[node_bge_embedding.py](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_bge_embedding.py:19) 每 5 个切片一批，把文本拼成：

```text
主体：BrotherHAK180烫金机，内容：切片正文……
```

生成：

```python
{
    "dense": [[float, float, ...]],       # 每条 1024 维
    "sparse": [{token_index: weight, ...}]
}
```

最终 chunk 形式为：

```python
{
    "chunk_id": 468027378355146793,
    "title": "## 设备",
    "parent_title": "## 设备",
    "part": 1,
    "file_title": "hak180产品安全手册",
    "item_name": "BrotherHAK180烫金机",
    "content": "...",
    "dense_vector": [0.01, -0.03, ...],   # 1024 个浮点数
    "sparse_vector": {4: 0.0128, 1173: 0.1699, ...}
}
```

如果序列化成 JSON，稀疏向量的整数键会变成字符串键。

### 8. Milvus 入库

项目创建两个集合：

- `kb_item_names`：商品名称级检索。
- `kb_chunks`：正文切片检索。
`kb_chunks` 字段包括：

```text
chunk_id       INT64 自动主键
content        VARCHAR
title          VARCHAR
parent_title   VARCHAR
part           INT8
file_title     VARCHAR
item_name      VARCHAR
dense_vector   FLOAT_VECTOR(1024)
sparse_vector  SPARSE_FLOAT_VECTOR
```

索引：

- Dense：HNSW + COSINE。
- Sparse：SPARSE_INVERTED_INDEX + IP。
- 稀疏检索算法：DAAT_MAXSCORE。

日志显示该链路曾成功识别商品并向 Milvus 插入 14 个切片。

## 五、SSE 与聊天记录的数据形式

SSE 基础设施在 [sse_utils.py](/Users/lwj/AI_project/RAG/app/utils/sse_utils.py:8)，每个 `session_id` 对应一个内存 `queue.Queue`。

传输格式例如：

```text
event: progress
data: {"status":"processing","done_list":["确认问题产品"],"running_list":["切片搜索"]}

event: delta
data: {"delta":"这"}

event: final
data: {"answer":"这是完整答案","status":"completed","image_urls":[]}
```

支持事件：

```text
ready / progress / delta / final / error
```

MongoDB 聊天记录设计为：

```json
{
  "_id": "ObjectId",
  "session_id": "sess-xxx",
  "role": "user 或 assistant",
  "text": "消息正文",
  "rewritten_query": "",
  "item_names": ["商品名称"],
  "image_urls": ["http://.../image.jpg"],
  "ts": 1787472000.123
}
```

但这些 MongoDB 方法目前没有被任何实际 API 调用。

## 六、数据最终存在哪里

| 位置 | 数据 |
|---|---|
| 进程内存 | LangGraph State、任务状态、节点进度、SSE 队列 |
| 本地 `output/` | 原文件、MinerU ZIP、Markdown、图片、解析 JSON、`chunks.json` |
| MinIO | Markdown 中引用的图片 |
| Milvus `kb_item_names` | 商品名称及其 Dense/Sparse 向量 |
| Milvus `kb_chunks` | 最终切片、元数据和双向量 |
| MongoDB `chat_message` | 计划存储对话历史，目前未接通 |
| Neo4j | 当前没有实际数据写入 |

项目没有配置 LangGraph checkpointer，所以图状态本身不会持久化；服务重启后，任务进度和 SSE 队列都会丢失。

## 七、当前最重要的问题

1. `query_server.py` 没有业务接口，完整查询服务尚未形成。

2. 查询图所有核心 RAG 节点仍是占位实现，已经写好的 Milvus 混合检索、Reranker、查询提示词都没有被调用。

3. 切片合并存在明确 bug：[node_document_split.py:223](/Users/lwj/AI_project/RAG/app/import_process/agent/nodes/node_document_split.py:223) 在不能合并时追加的是当前 `section`，而不是前一个 `pre_section`。现有样例已经出现最后一个切片重复两次，也可能丢失第一个前导块。

4. Milvus 重新导入时按 `item_name` 删除旧数据。同一个产品如果有“安全手册”和“使用说明书”两份文档，后导入的可能删除前一份的全部切片。

5. `.env` 中 `EMBEDDING_DIM=1536`，代码和 BGE-M3 实际使用 1024 维；环境配置目前没有生效。Reranker 路径还指向了 BGE-M3，而不是 reranker 模型。

6. 图片目录不存在时，`node_md_img` 直接返回，没有把节点从运行中移到已完成，前端进度可能一直显示“Markdown 图片处理中”。

7. MongoDB 的 `get_recent_messages()` 使用“时间升序后 limit”，实际拿到的是最早 N 条，不是最近 N 条。

8. 任务状态和 SSE 都只存在单进程内存中，不支持多 worker、服务重启、任务恢复，也没有自动清理机制。

9. 上传文件名和 MinerU ZIP 解压路径缺少安全处理；同时没有认证、文件大小限制，MinIO 桶还被设置为匿名可读，不适合直接暴露到生产环境。

10. 测试目前是脚本式测试，没有 pytest 依赖和断言体系。56 个 Python 文件都能通过语法解析，但查询测试验证的只是占位答案。

综合来看，项目当前最准确的定位是：

> “已经跑通的文档入库系统 + 已搭好架构但尚未实现核心检索的查询原型。”

下一步开发优先级应是：先修复切片正确性和 Milvus 删除策略，再完成 `query_server.py`，随后依次接通商品确认、Milvus 混合检索、HyDE、RRF/Rerank、答案生成和 MongoDB 历史。
