# 回答依据校验：第一版

查询流程现在是：商品确认 → 多路检索 → RRF → 重排 → 资料适用性校验 → 生成完整草稿 → 回答依据复核 → 发送及保存。

## 当前规则

- 尚未接入可信的单机检测服务。网页、说明书、用户粘贴的报告、历史助手回答，以及资料自称的 `verified` 标记，都不能作为单机状态证据。第一版没有根据这些输入放行健康度数值或故障结论的分支。
- 明显的单机健康度、故障等请求由规则直接返回缺少检测依据的说明；其他措辞由语义分类补充识别。通用定义、型号规格、检测查询方法和有依据的条件式排查仍可回答。
- 系统版本只取自用户原话中的明确声明或明确指定的操作目标版本，不能从改写问题、助手历史、网页或型号推断。用户声明用于匹配操作说明，不代表系统已经实测确认。
- 版本不匹配、Windows 10 未明确是否为 CMIT、版本未知、系统依赖资料没有明确版本、存在矛盾时，不给对应操作。硬规则对 Windows 版本及 CMIT/家庭/专业/企业/教育版做显式匹配，也识别部分其他系统的数字版本。
- 资料中的版本标记和文件名会参与匹配。第一版按整个片段保守排除，可能同时排除其中与系统无关的硬件说明；多系统混合步骤不会自动拆分放行。当前重排已经淘汰的片段不会在核验后重新召回。
- 语义核验只接受字段完整、类型正确的 JSON，资料编号必须完整且有效。超时、格式错误、证据不足或答案复核失败时使用固定回复，不退回未经核验的生成。
- 草稿逐句检查事实依据、单机断言和系统适用性；健康度具体百分比及显式系统不匹配另有程序规则。旧助手回答不再放入答案生成的参考上下文。
- SSE 继续发送进度事件，完整答案通过复核后才发送一个 `delta`；图结束仍由原接口发送 `final`。MongoDB 只保存最终允许发送的文本。被拦截答案不附带检索图片。

## 配置及上线

无需修改 `.env` 或重建知识库，规则默认生效，没有通过环境变量跳过校验的开关。重启查询服务以加载新的代码和提示词。

正常生成最多增加两次模型调用：资料适用性校验、草稿复核；使用既有 `LLM_DEFAULT_MODEL`，校验调用单独传入温度 0、单次请求超时 30 秒，沿用模型客户端的重试策略。`.env` 里的其他模型调用温度不变。

主要文件：

- `app/query_process/agent/evidence_guard.py`：硬规则、严格响应解析、固定回复及校验逻辑。
- `app/query_process/agent/nodes/node_evidence_guard.py`：重排后的核验节点。
- `prompts/evidence_check.prompt`、`prompts/answer_review.prompt`：语义分类及独立复核规则。
- `prompts/answer_out.prompt`：生成阶段的证据边界。

## 验证

离线回归不连接数据库或模型：

```sh
LOG_CONSOLE_ENABLE=false LOG_FILE_ENABLE=false .venv/bin/python -m unittest app.test.test_evidence_guard app.test.test_query_kg -q
```

覆盖电池健康度、隐含单机结论、伪造检测报告、普通资料问答、Windows 10/11/CMIT、版本纠正、助手历史污染、未知及冲突范围、核验失败、同步/SSE/历史一致性和主图连线。

2026-09-15 还使用 `.env` 配置的真实模型进行了人工构造样例验证：普通开机说明的生成及复核通过；“这台能放心用吧”被判为缺少单机证据；系统未知时 CMIT 步骤被拦截；明确使用 Windows 10 CMIT 时对应资料放行，Windows 11 专业版时被排除。此验证只调用模型，不访问设备记录或数据库，不代表全量客服场景的准确率评估。

## 边界及后续

这是分层防护，不是任意自然语言下零误判的证明。语义分类和复核仍依赖模型，硬规则对模糊表达和复杂版本组合采用保守拒答；应持续用真实客服问题评估误放行和误拒答。

接入单机报告时需另行实现可信服务查询、设备标识绑定、检测时间及指标验证、冲突处理。不能仅增加一个来自请求或检索文本的 `verified=true` 字段来开放单机结论。即使有报告，也只能描述该设备在对应检测时点的记录。
